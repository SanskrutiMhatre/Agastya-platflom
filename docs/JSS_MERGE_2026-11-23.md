## The conflicts, why they happened, and what was chosen

**1. Line endings (every file looked conflicting; none were).** The source files carry mixed LF and CRLF lines (the repository normalises to LF on commit, tools on Windows write CRLF).
A merge on the raw files reported one whole-file conflict in each of the six shared files. Merged on LF-normalised text, the same six files merge with **no** conflict - the two sides edited
different places. Resolution: merge normalised, write back CRLF; the diff against the previous commit is then exactly the JSS copy's own change (12, 19, 13, 25, 2 and 2 lines), no noise.

**2. The guards that froze the S1000D engine (the real conflict).** The JSS copy's `jss-cover-isolation.test.js` proves its stylesheet change cannot move an S1000D build in two ways:
a SHA-256 manifest of every `vendor/pipeline/s1000dtofo` file, and a fingerprint of the XSL-FO of three builds. This line edits `s1000dtofo` on purpose, so the manifest could never pass.
Measuring first, on both untouched trees, with the same method:

* the three fingerprints differed between the two trees by 12, 9 and 12 characters - and from the stored values by different amounts in each tree;
* the cause is **not** content: the FO contains the relative path from the build folder to `vendor/.../intentionally-blank.svg`, which depends on **where the repository is checked out**
  (the stored fingerprints could only ever pass in the folder they were taken in), and the S1000D stylesheets emit attributes in a different order after our refactor;
* with the checkout location and the attribute order ignored (`canon()` in the test), the two trees give **identical** FO for all three builds. So the JSS edits do not move S1000D, and the S1000D
  edits do not move the old JSS path - which is what the guard exists to prove.

Options that were weighed:

| Option | What it means | Verdict |
| --- | --- | --- |
| A. Keep the manifest, re-baseline it to today's `s1000dtofo` | the guard stays byte-exact, but every intended S1000D stylesheet change from now on fails a JSS test and needs a manifest edit | rejected: it blames the JSS work for S1000D changes |
| **B. Canonical fingerprints + "one include" test** (chosen) | fingerprints ignore location and attribute order; the manifest is replaced by a test that the S1000D engine reaches `jsstofo/` through one include only (`frontmatter-shared.xsl` -> `../jsstofo/frontmatter.xsl`) | one way in for a JSS edit, and the fingerprint exercises exactly that file inside an S1000D build |
| C. Drop the S1000D guards | | rejected: the exception's whole safety argument rests on them |

The new baseline values are the ones both pre-merge trees agreed on; the merged tree reproduces them (`jss-cover-isolation` 6/6).

**3. Arial Narrow (a gap, not a text conflict).** The JSS stencils set headings in Arial Narrow; `fop.xconf` now names its four files. They are proprietary, not in `C:\Windows\Fonts`, and git-ignored
like Arial (`/backend/vendor/tools/fonts/arial*.ttf` already matches). `engine/fontconf.js` leaves a missing face out, so a machine without them still builds (headings fall back to Arial / Liberation Sans).
The installer script already copies and excludes `arial*.ttf` by pattern, but its licence notice said "four Arial files"; it now names Arial Narrow too. **Decision for the owner:** shipping Arial Narrow
in the installer has the same licence position as shipping Arial (decided earlier: shipped, with `--no-arial` to leave them out).

**4. Constraint kept.** The branch history is only ever added to: `origin/main` already holds `57dbe5b`.
